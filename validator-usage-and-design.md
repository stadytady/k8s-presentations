# Validator в GPU Operator: как используется и как его проектировать

Продолжение к `nvidia-operator-validator.md`, где разобрано, **как** validator работает внутри.
Здесь — **кто** потребляет его результат и какие правила из этого следуют для своего оператора.

| Репозиторий | Коммит | Что смотрел |
|---|---|---|
| NVIDIA/gpu-operator | `304898f` (18.11.2026) | `cmd/gpu-operator/main.go`, `controllers/object_controls.go` (`isDaemonSetReady`, `TransformValidator*`), `cmd/nvidia-validator/*`, `assets/state-*` |
| NVIDIA/k8s-operator-libs | `42ee2ff` (20.10.2026) | `pkg/upgrade/validation_manager.go`, `upgrade_state.go`, `consts.go` |

Факты из кода помечены ссылкой на файл. Рекомендации по проектированию — мои выводы, а не документация NVIDIA.

## 1. Кто потребляет результат validator'а

| Потребитель | Что смотрит | Когда | Где в коде |
|---|---|---|---|
| Операнды на той же ноде | маркеры `/run/nvidia/validations/*-ready` | **только при старте пода** (init-контейнер или entrypoint) | `assets/state-device-plugin/0400_configmap.yaml`, init `toolkit-validation` в GFD, dcgm-exporter, mig-manager |
| Статус ClusterPolicy | готовность DaemonSet `nvidia-operator-validator` | на каждом reconcile | `controllers/object_controls.go` → `isDaemonSetReady` |
| Апгрейд драйвера | Ready пода `app=nvidia-operator-validator` на конкретной ноде | в состоянии `validation-required` | `cmd/gpu-operator/main.go:187`, `k8s-operator-libs/pkg/upgrade/validation_manager.go` |
| Мониторинг | метрики `gpu_operator_node_*` | постоянно | `cmd/nvidia-validator/metrics.go` |
| Человек | `kubectl get pod` (`Init:N/4`), логи init-контейнера | при разборе | — |

### 1.1 Статус ClusterPolicy

`isDaemonSetReady` считает DaemonSet готовым, только если выполнены все условия:

- `status.observedGeneration >= generation` — контроллер DaemonSet увидел последнюю версию;
- `status.numberUnavailable == 0`;
- для RollingUpdate rollout завершён (`isDaemonSetRollingUpdateComplete`); для OnDelete — проверки ревизий по подам.

Под validator'а становится Ready, только когда прошли **все** init-контейнеры и запущен основной. Отсюда:
**хотя бы одна GPU-нода не прошла проверку → DaemonSet validator'а unavailable → ClusterPolicy `notReady`.**

### 1.2 Апгрейд драйвера

```go
// cmd/gpu-operator/main.go
upgrade.NewClusterUpgradeStateManager(...).
    WithPodDeletionEnabled(gpuPodSpecFilter(ctx, mgr.GetAPIReader())).
    WithValidationEnabled("app=nvidia-operator-validator")
```

В `k8s-operator-libs/pkg/upgrade/validation_manager.go`:

- `Validate(node)` ищет поды по `podSelector` с `spec.nodeName=<node>`;
- под считается готовым, только если **все** `containerStatuses[].ready == true` (`isPodReady`);
- если не готов, считается таймаут от времени входа в состояние; `validationTimeoutSeconds = 600`;
- таймаут истёк → нода переходит в `upgrade-failed`.

Цепочка апгрейда по лейблу `nvidia.com/gpu-driver-upgrade-state`:

```text
upgrade-required → cordon-required → wait-for-jobs-required → pod-deletion-required → drain-required
→ pod-restart-required → validation-required → uncordon-required → upgrade-done
                              └─ 600 с без Ready validator'а → upgrade-failed
```

Вывод: **upgrade-контроллер ничего не знает о драйверах и CUDA.** Он ждёт Ready у пода с заданным лейблом.
Вся предметная логика проверки спрятана в validator.

### 1.3 Чего validator НЕ делает

- Не останавливает работающие операнды, если маркер пропал: маркеры читаются только при старте.
- Не перепроверяет ноду сам по себе после успешного прохода: init-контейнеры выполняются один раз за жизнь пода.
- Не пишет Condition на Node или ClusterPolicy по каждой ноде: деталь видна только в статусе пода и в метриках.

## 2. Главная идея: Ready пода — это API

«Нода прошла проверку» ≡ «под validator'а на этой ноде Ready».

| Плюс | Почему |
|---|---|
| Ничего не нужно изобретать | не нужен свой CRD, Condition или аннотация на Node |
| Понятно всем | оператор, upgrade-контроллер, kubectl, ArgoCD health, `kubectl wait` |
| Дёшево | kubelet уже пишет статус пода, лишних записей в API нет |
| Диагностика из коробки | имя застрявшего init-контейнера = сломанный слой |

| Минус | Как компенсировать |
|---|---|
| Ready фиксируется один раз: init не перезапускается | периодическая перепроверка в метриках (раздел 4.3) |
| Нет причины в статусе CR | агрегировать в `status.conditions` своего CR (раздел 6) |
| Под удалили → все маркеры удалены → ноду считают «не прошедшей» | для работающих операндов это безопасно: маркеры читаются только при старте |

## 3. Два уровня валидации — не путать

| | Уровень кластера | Уровень ноды |
|---|---|---|
| Вопрос | «оператор задеплоен и работает?» | «эта нода готова принять операнд?» |
| Форма | Job: `helm test` / ArgoCD PostSync hook | DaemonSet на целевых нодах |
| Проверяет | CRD установлен, RBAC, Ready оператора, `status` CR сошёлся | драйвер, runtime, устройства, сквозной тестовый под |
| Живёт | минуты, после деплоя | всё время, пока есть нода |
| Потребитель | CD-пайплайн (Helm, ArgoCD) | операнды, upgrade-флоу, статус CR, мониторинг |
| Пример | `dummy-op validate` (PR #23) | `nvidia-operator-validator` |

Начинать стоит с уровня кластера: он нужен всегда. Узловой validator нужен, **только если у операнда есть зависимости на хосте** (модуль ядра, runtime, устройство, файловая система).

## 4. Правила проектирования узлового validator'а

### 4.1 Три канала, каждый для своей аудитории

```text
                    ┌──────────────────────────┐
                    │  validator (DaemonSet)   │
                    └──┬──────────┬──────────┬─┘
     маркеры hostPath  │  Ready   │ метрики  │
                       ▼   пода   ▼          ▼
     операнды на ноде     оператор,      Prometheus/алерты
     (init/entrypoint)    upgrade,       (работающая нода)
                          kubectl
```

| Канал | Аудитория | Без него |
|---|---|---|
| Маркер-файлы на hostPath | процессы на той же ноде | операндам пришлось бы ходить в API, чтобы узнать готовность соседей |
| Ready пода | всё вне ноды | нужен свой статус и свой протокол |
| Метрики с перепроверкой | мониторинг работающей ноды | деградация после старта не видна до перезапуска пода |

Если сделать только первые два канала, драйвер, отвалившийся через неделю, никто не увидит.

### 4.2 Маркер-файлы

| Правило | Зачем | Как у NVIDIA |
|---|---|---|
| Каталог на tmpfs: `/run/<operator>/validations` | перезагрузка сбрасывает маркеры вместе с загруженными модулями, отдельная инвалидация не нужна | `/run/nvidia/validations` |
| Удалять маркер **до** проверки | не будет ложного «ready» от прошлого прохода во время перепроверки | `deleteStatusFile` в начале каждого `validate()` |
| Писать атомарно: `tmp` + `rename` | потребитель не прочитает недописанный файл | `utils.WriteFileAtomically`, `mv` в startup-probe драйвера |
| Внутри — env-файл с фактами | потребитель получает параметры, а не только «готово» | `driver-ready`: `NVIDIA_DRIVER_ROOT=…` и т.д., device-plugin делает `source` |
| Удалять в `preStop` | удалённый под validator'а не оставляет «ready» | `rm -f /run/nvidia/validations/*-ready` |
| Потребитель проверяет и маркер, и живое состояние | защита от устаревшего маркера | `toolkit-ready && initstate == live` |

### 4.3 Перепроверка работающей ноды

Init-контейнеры отрабатывают один раз. Для работающей ноды нужен отдельный периодический цикл:

- основной контейнер validator'а (или sidecar) раз в N минут повторяет **дешёвые** проверки, например `nvidia-smi`;
- результат пишется в метрики: `*_ready` (0/1) и `*_last_success_ts_seconds`;
- алерт строится по **возрасту** последнего успеха, а не только по 0/1: так ловится и «проверка упала», и «проверка зависла».

```yaml
# пример правила
- alert: NodeValidationStale
  expr: time() - acme_node_validation_last_success_ts_seconds > 900
  for: 5m
```

Сквозной тестовый под периодически **не** гонять: он тяжёлый и конкурирует с нагрузкой.

### 4.4 Шаги по графу зависимостей

- Один init-контейнер на один слой, порядок — по зависимостям (у NVIDIA: driver → toolkit → cuda → plugin).
- Каждый шаг проверяет **только свой слой** и считает, что нижние прошли.
- Имя упавшего init-контейнера сразу говорит, какой слой сломан.

Анти-паттерн: один `check-all.sh`. Тогда в статусе только «что-то не так», и разбор начинается с чтения логов.

### 4.5 Ждать или падать

| Режим | Когда | Почему |
|---|---|---|
| Цикл внутри (`WITH_WAIT=true`) | зависимость готовится **долго** (сборка драйвера — минуты) | CrashLoopBackOff дорастает до 5 минут; нода простоит до 5 минут **после** того, как зависимость готова |
| Выход с ошибкой | быстрая проверка, которая либо проходит, либо нет | ошибка видна в статусе (`Init:CrashLoopBackOff`), backoff бережёт API |

В обоих режимах нужен **предел**: у cuda-пода 60×5 с, у апгрейда 600 с. Бесконечное ожидание без статуса — худший вариант: нода «висит», и никто не понимает почему.

### 4.6 Сквозная проверка реальной нагрузкой

Как делает NVIDIA (`cmd/nvidia-validator/main.go`, `runWorkload`):

- отдельный Pod из манифеста в образе;
- `spec.nodeName = <нода>` — в обход планировщика, под гарантированно на проверяемой ноде;
- `ownerReferences` скопированы с DaemonSet'а validator'а — GC уберёт под вместе с владельцем;
- tolerations, образ, pullSecrets, runtimeClass взяты с DaemonSet'а;
- предыдущий тестовый под удаляется перед созданием нового;
- ожидание `phase == Succeeded` ограничено по времени.

Правило: **не потреблять ресурс, ради которого всё делается.** Проверка cuda получает GPU через CDI-аннотацию без запроса `nvidia.com/gpu`. Тест с реальным выделением GPU (`WITH_WORKLOAD` у plugin) в DaemonSet выключен. Причина в коде не написана, но на занятой ноде такой тест конкурирует с нагрузкой за GPU.

### 4.7 Validator не должен быть точкой отказа

- Работающие операнды не зависят от validator'а: маркеры читаются только при старте. Если validator сбоит, нагрузка продолжает работать. Каскадного отказа нет.
- Не вешать на validator liveness-пробы операндов.
- Не перезапускать операнды при пропаже маркера.
- Оператор может считать ноду «не готовой» (статус, алерт), но не должен из-за этого ничего удалять с ноды.

### 4.8 Безопасность

| Что | Правило |
|---|---|
| `privileged` | только шагам, которым нужен хост. Проверку «объект есть в API» можно делать без привилегий |
| hostPath | только нужные каталоги, по возможности read-only. NVIDIA монтирует `/` в `/host` для поиска драйвера на хосте — это осознанная плата за поддержку host-драйвера |
| RBAC | `get nodes` (ClusterRole); `create/delete/list pods` для тестовых подов — **Role в своём namespace**, не ClusterRole |
| ServiceAccount | отдельный для validator'а, не общий с оператором |
| Тестовый под | ownerRef + таймаут + удаление; иначе на каждой ноде копятся `Completed`-поды |

## 5. Чек-лист перед реализацией

- [ ] Понятно, какой уровень нужен: кластер (Job), нода (DaemonSet) или оба.
- [ ] Граф зависимостей слоёв нарисован; один init-контейнер на слой.
- [ ] У каждого шага решено: ждать в цикле или падать; у каждого ожидания есть предел.
- [ ] Маркеры: tmpfs, удаление до проверки, атомарная запись, env-содержимое, `preStop`.
- [ ] Потребители проверяют маркер **и** живое состояние.
- [ ] Ready пода validator'а используется как сигнал готовности ноды (статус CR, upgrade).
- [ ] Есть периодическая перепроверка и метрики `*_last_success_ts_seconds` + алерт по возрасту.
- [ ] Сквозной тест не потребляет целевой ресурс или выключен по умолчанию.
- [ ] Отказ validator'а не останавливает работающую нагрузку.
- [ ] `privileged` и hostPath — минимально; RBAC на поды — Role в своём namespace.
- [ ] e2e: нода без зависимости → validator застревает на нужном шаге; зависимость появилась → Ready; перезагрузка → цепочка проходит заново.

## 6. Как это легло бы на dummy-op

**Сейчас узловой validator не нужен.** Операнд — заглушка без зависимостей на хосте. Кластерный Job из PR #23 (`dummy-op validate`, hook `helm test` / ArgoCD PostSync) уже проверяет цепочку NFD → src-лейбл → gating → DaemonSet.

Когда появится реальный операнд с драйвером или устройством, схема такая:

| Компонент | Что делаем | Какой инвариант AGENTS.md затрагивает |
|---|---|---|
| DaemonSet `dummy-op-validator` | тот же nodeSelector по `deployLabel`, что у операнда; только в `--namespace` | 5 (выбор нод по deploy-лейблу), 6 (DS только в своём namespace) |
| Init-шаги | по слоям операнда; маркеры в `/run/acme/validations/<policy>/` | — |
| Операнд | init-контейнер ждёт маркер **и** живое состояние | 2 (`mutateDS` трогает только свои поля — init добавлять аккуратно) |
| Статус политики | `computeStatus` учитывает Ready validator'а по нодам: `Ready=False`, `reason=NodeValidationFailed`, в `message` — число нод | 1 (идемпотентность: статус пишется только при изменении) |
| RBAC | `create/delete/list pods` — Role в `--namespace`; маркеры RBAC генерировать, в шаблоны руками не дописывать | 6, 10 |
| Метрики | `acme_node_validation_ready{policy,node}`, `acme_node_validation_last_success_ts_seconds`; удалять серии при удалении политики | 13 |
| Тесты | unit: `computeStatus` с готовыми и неготовыми подами validator'а; envtest: wiring; e2e на kind: сценарий «нода без зависимости → validator застревает» | раздел «Тесты» |

Открытые вопросы до реализации:

1. Нужна ли пауза на уровне ноды: например, лейбл `acme.io/validation.skip=true` по аналогии с `gpu-driver-upgrade.skip`.
2. Где держать per-node причину: только в статусе пода и метриках (как у NVIDIA) или агрегировать в `status` политики. Агрегация удобнее, но на больших кластерах это частые записи status — нужен дебаунс.
3. Нужен ли свой upgrade-флоу. Если операнд обновляется через RollingUpdate DaemonSet, а не OnDelete, хватит readiness операнда, и state-машина как у NVIDIA не нужна.
